## 3 — Open, with what each would cost

- **A CUDA PyTorch wheel.** CUDA is on this Jetson and works — CUDA 12.6,
  `nvcc V12.6.68` — but `torch 2.3.1` here is a **CPU-only build**
  (`torch.version.cuda = None`), and `_load()` sets
  `torch.set_num_threads(1)` on purpose after 9 Oct. So LighterGlue's 1.9 s is
  one CPU core. NVIDIA's Jetson wheel would move it to the GPU. **This is the
  one lever that attacks the biggest cost and never touches the flow**, because
  the matcher only runs above 60 m.
- **The flow on the GPU: not through OpenCV.** This OpenCV 4.8.0 reports
  **0 CUDA devices** and no OpenCL (Tegra ships none). It is built with TBB
  and already uses all six cores — `getNumThreads() = 6`, which is why cpu_pct
  reads 275% and why the unnamed `python3` threads at 34% in the load log are
  TBB workers. Spreading across cores is already done; there is nothing to win
  there.
- **VPI 3.2.4 is installed** (`/opt/nvidia/vpi3`, backends CUDA PVA OFA VIC)
  and has both hot operations — Harris corners and pyramidal LK. It could not
  be tested from this shell: `vpi.asimage()` fails with `EGL_BAD_DISPLAY`, no
  display context. Needs trying from the desktop session.
- **The camera's own FeatureTracker** (depthai 2.33 has the node) would cost
  the Jetson nothing for detection and tracking — but it does **not** end the
  Jetson's work: per-track derotation, the depth gate, `flow_disagree` and
  dual-flow all stay. It replaces `FlowTracker._detect` and `.step`, so new
  corners, new sub-pixel behaviour, no forward-backward check — i.e. it
  changes the flow **below 60 m**, which the standing rule forbids. It also
  adds a stream to a USB 3 link already carrying 410 Mbit/s on a machine with
  recorded `Input/output error` LPM faults. Not a small change and not safe to
  start next to a flight.
- **`relocate()`** is built and tested offline (131 m -> 5.24 m) and still
  **not wired in**. It needs confirm-before-commit logic first.
- **XFeat `top_k` 512 per call** for the mutual-NN path only, keeping 1024 for
  LighterGlue — `detectAndCompute` reads `model.top_k` at call time, so it is
  possible. Worth 40 ms on the matcher that was already cheap. Smallest item
  on this list; mentioned only so it is not re-derived.
- **TRACK LOST has no hysteresis.** One frame at 29 tracks sends a CRIT, the
  next at 31 sends OK; that is 788 flips in 6299 ground rows. It is an
  announcement change, not a data change, and the pilot has not approved it.

## 4 — Still true from before, do not re-derive

- The flow works below 50-60 m and **nothing may change its behaviour there**.
  25 Oct flight 245: 634 s on the VPS, zero ALT_HOLD, 0.44 m at 38 m.
- `EK3_SRC1_VELXY = 0` — our velocity never reaches the EKF. Say nothing about
  phantom velocity reaching the controller without reading the parameters.
- Score position **only** against `gps1_north_m`/`gps1_east_m`, never
  `gps_north_m`, which is our own injection coming back. Filter `gps1_*` rows
  beyond ~400 m of origin; corrupt rows exist. Never take the declared sigma
  from the receiver. Call it the **M9N**; GPS1/GPS2 mean the FC's two ports.
- Reconstruct the origin per row (`origin = lat - north/MDEG`). The handover
  re-anchors it, and using one origin for a whole flight splits one track into
  two legs that were never flown.
- `systemctl restart drone-vps` kills the camera. Always **stop**, wait for
  `03e7:2485`, then **start**.
- ALT_HOLD is what the aircraft falls back to, never LAND, and ALT_HOLD is a
  thing to avoid, not a solution.
